# 一次加法在硬件里走完 11 步

写 `c = a + b` 的时候，脑子里是一个动作。真跑起来是一串：指令要先从磁盘搬进内存，再搬进缓存，再进 CPU；算完的结果还要反向走一遍，最后交给屏幕上的一个像素。

## 为什么值得拆开看

因为性能问题九成出在这条路上，而不是出在"加法"本身。一次 64 位整数加法大约 1 个周期，一次主存访问是它的几百倍。**算法快不快，常常取决于你让 CPU 等了多少次内存**，而不是你少做了几次加法。

## 五个阶段各自在等什么

| 阶段 | 干什么 | 典型瓶颈 |
| --- | --- | --- |
| 取指 Fetch | 按 PC 从指令缓存里取指令 | 指令缓存未命中，要回主存取 |
| 译码 Decode | 认出这是 `ADD`，读寄存器 | 依赖上一条指令的结果，要等 |
| 执行 Execute | ALU 把两个数加起来 | 基本不耗时，1 个周期 |
| 访存 Memory | 读操作数 / 写结果 | 缓存未命中，几十到几百个周期 |
| 写回 Write Back | 结果写回寄存器或内存 | 通常不是瓶颈 |

注意中间那两行：**真正干活的那一步几乎不花时间，时间都花在"把数据搬过来"**。这就是为什么整个存储层级（寄存器 → L1 → L2 → L3 → 主存 → SSD）设计得这么复杂。

## 数量级感受

| 操作 | 大约延迟 | 换算成人话（1 周期 ≈ 1 秒） |
| --- | ---: | --- |
| 寄存器访问 | 1 周期 | 1 秒 |
| L1 命中 | ~4 周期 | 4 秒 |
| L2 命中 | ~12 周期 | 12 秒 |
| L3 命中 | ~40 周期 | 40 秒 |
| 主存 | ~200 周期 | 3 分钟 |
| SSD 读取 | ~100 微秒 | 一天多 |
| 磁盘寻道 | ~10 毫秒 | 几个月 |

这张表是理解一切性能优化的起点：**同样一次"访问"，跨一层就是几十倍**。

## 回到代码

```c
int add(int a, int b) {
    return a + b;
}
```

编译器生成的大概是三条指令：把两个参数从内存/寄存器搬到 ALU 的输入、相加、把结果搬回去。三条指令里，真正"算"的只有中间那条。

所以想让它更快，方向通常不是换算法，而是：

1. 让数据留在缓存里（数据局部性）；
2. 让 CPU 能提前猜到下一步（分支预测、预取）；
3. 让多条指令重叠执行（流水线、乱序执行）。

## 三个常见误解

- **"加法很快"** —— 加法本身快，取数据不快。
- **"CPU 主频越高越快"** —— 主频只压缩了计算那一格，内存墙没动。
- **"编译器会帮我优化"** —— 它能在指令层面调度，但改不了你的数据放在哪。
