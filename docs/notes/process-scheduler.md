## 三个状态，一条环

进程在任意时刻只有三种身份：

- **运行 Running**：正占着一个核；
- **就绪 Ready**：万事俱备，只差一个核；
- **阻塞 Blocked**：在等 I/O 或锁，给它核也没用。

状态之间的转移只有四条边：就绪 → 运行（被调度）、运行 → 就绪（时间片用完 / 被抢占）、运行 → 阻塞（发起 I/O）、阻塞 → 就绪（I/O 完成）。

有意思的是**没有"阻塞 → 运行"这条边**：等 I/O 回来的进程不能直接跳上 CPU，必须先回到就绪队列重新排队。这条规则是为了公平——不然一个 I/O 密集的进程回来就插队，CPU 密集的进程会被饿死。

## 时间片是骗局吗

把时间片调小，看起来更"公平"、响应更快，但每个切换都有成本：

| 时间片 | 切换开销占比 | 感受 |
| ---: | ---: | --- |
| 1 ms | 高 | 响应快，但大量时间在保存/恢复现场 |
| 10 ms | 低 | 桌面系统的常见选择 |
| 100 ms | 极低 | 吞吐高，但交互会卡顿 |

Linux 的 CFS 早就不再用固定时间片，而是按**权重分配 CPU 时间**：每个进程记一笔"虚拟运行时间"，调度器永远挑欠账最多的那个跑。优先级高的进程虚拟时间涨得慢，自然被挑中得多。

## 上下文切换到底吃多少

一次切换要做的事：保存当前进程的寄存器、栈指针、页表基址；切换地址空间（可能冲刷 TLB）；恢复下一个进程的现场。直接成本大概几微秒，**间接成本才是大头**——缓存和 TLB 被搅乱，新进程一开始几乎全部未命中。

所以在演示里把时间片拖到很小，你会看到总完成时间反而变长：不是调度器变笨了，是它在做无用功。

## 演示里那三个旋钮

1. **核数**：从 1 调到 4，看就绪队列怎么缩短。
2. **进程数**：超过核数越多，等待时间线性增长——这就是排队论的直观版本。
3. **时间片**：观察"响应快"和"总耗时短"之间的反向关系。
